# 修復 bug

系統化修復使用者描述的一個 bug（症狀：$ARGUMENTS）。核心原則：**先觀察再動手、修根因非症狀、最小變更、改動須被測試證明**。逐階段進行，勾選項目確認完成，遇到標註「**⏸ 等使用者確認**」處停下等回覆再繼續。

## 依序執行

### 1. 確認症狀與重現

- [ ] 用自己的話覆述症狀，推測涉及的頁面與請求流程（Controller → Service → Repository）。
- [ ] 找出精確觸發條件：輸入、資料狀態、操作步驟。若無法穩定重現，先蒐集資料，**勿盲修**。
- [ ] **⏸ 等使用者確認** 你對症狀與重現步驟的理解無誤。

### 2. 觀察並定位根因

- [ ] 先讀相關 Core service 與其 test，確認領域規則（status 轉移、pricing/discount、stock）。修改前勿假設既有程式正確 — 部分行為刻意不完美。
- [ ] 沿失敗路徑追蹤實際資料流，用實際值（讀程式、必要時加暫時 log）驗證，**別用猜的**。
- [ ] 逐一縮小範圍：比對「會失敗 vs 會成功」的差異；分而治之。必要時 `git bisect` 找出引入 regression 的 commit。
- [ ] 問「什麼條件讓此失敗必然發生」，追到可行動的根因（常是缺驗證、錯誤假設、折扣套用位置/次數），而非表面症狀。先排除低階原因（stale build、錯分支/設定）。
- [ ] 搜尋改動點的所有呼叫端，確認同一 bug pattern 未散落他處、修復不會破壞其他路徑。
- [ ] **⏸ 等使用者確認** 根因說明後，再動手修。

### 3. 最小變更修復

- [ ] 只改修根因所需的程式；**不順手重構、格式化或清理無關程式碼**（會污染 review、破壞 revert/bisect）。
- [ ] 遵循分層慣例：商業邏輯留在介面後的 Core service，資料存取經 repository，view 綁 ViewModel。新使用者可見文字用繁體中文。
- [ ] 保持 CRLF line endings。

### 4. 回歸測試（先紅後綠）

- [ ] 在對應關注點的 test class（如 `OrderServiceCancelTests`）新增回歸測試，重用 `TestSetup.cs` 的 factory helper。
- [ ] 確認該測試在**修復前的邏輯下會失敗**、修復後通過 — 證明改動確實修好此 bug。
- [ ] 用 **test-runner** agent 先以 `--filter` 迭代，最後跑完整 `dotnet test` 一次確認全綠；並執行 `dotnet build` 通過。

### 5. 審查與實測

- [ ] 用 **code-reviewer** agent 審查改動（正確性、分層慣例、副作用）。
- [ ] 提示使用者回實際頁面重跑第 1 步的重現步驟，確認症狀消失。

### 6. Commit

- [ ] **⏸ 等使用者確認** 後，由 `main` 開聚焦分支（若尚未），以「症狀 → 根因 → 修法」格式撰寫 commit message 並 commit。一個 commit 只含此修復。

## 常見陷阱

- 修症狀而非根因 → bug 換個形式復發。
- 未觀察就臆測 → 改到無關程式、引入新 bug。
- 變更過大 / 混入重構 → 無法歸因、破壞 bisect。
- 無「先紅後綠」的回歸測試 → 無法證明修好，日後可能靜默復發。
- 只跑新測試、未跑完整套件 → 漏掉 regression。
